Statement Tracker Dashboard

Complement the monthly/quarterly statement tracking ops does today in Excel — reduce the burden, increase efficiency, and cut the time spent chasing and logging statements. A statement hits Canoe → the API registers it → the dashboard updates with Firm, Fund, and the period it covers. Entirely metadata-and-rules — this track carries no Gen AI dependency.

The reference architecture

How a statement becomes a tracked filing

Everything before the reconciliation engine is a scheduled poll against endpoints the downloader already uses. Everything after it is deterministic rules — no document body is ever opened.

Green / amber / red outcomes map directly to the dashboard's status pills. Canoe's three review flags never auto-confirm a period — they route to the review queue, which is the tracker's most important view given the known data-date tagging gap.
The two versions

Compliant today vs. better with approval

Architecture A is unusual in that its baseline is already fully compliant — it reads no document content at all. The upgrade path is about closing the data-date gap that otherwise lands on a person's desk.

Version 1 · Build now

Deterministic, no document content read

Pure metadata + rules. The system reads Canoe's structured fields (fund, entity, data_date, status) — never the file body. All data stays local on the Mac Mini or inside the M365 tenant.

  • Uses Canoe's data_date as-is
  • Any flagged status or missing/implausible date → human-review queue
  • Dashboard as a local app or a SharePoint/Power BI view (both in-tenant)
  • No new tool, no new data-handling — nothing to approve
✔ Compliant under current policy · no AI review needed
Version 2 · Needs approval

+ narrow LLM pass to fix the data-date gap

Adds one tightly-scoped model call that reads only the "as of / period-end date" from statements Canoe mis-tagged or left blank — the single biggest driver of manual review today.

  • Automates the team's #1 pain point instead of queuing it
  • Extracted date validated against the expected period (deterministic check)
  • Token cost near-zero: runs only on exception docs, cheapest model, one field
  • Sends statement content to an LLM → triggers the compliance gate
▲ Requires IT Lead/CTO review (financial-document content)
Why v2 is worth requesting

The whole reason a passive "list what arrived" view isn't sufficient is that Canoe frequently gets the data date wrong — and the data date is the field that answers "which period does this statement cover." Version 1 handles that safely by sending every questionable date to a human. Version 2 removes most of that manual work by having a model read the one date off the page, then checks its answer against what the schedule expected. It's the highest-leverage, lowest-token use of AI in the entire project — but because it puts statement content in front of a model, it belongs to the same approval path as Architecture B. See the compliance gate.

Sequence

Build phases

A1

Metadata store

Extend the poller to upsert full document + allocation metadata into a DB rather than a flat ID list. Storage upgrade only — no change to what's downloaded.

A2

Expected-schedule setup

Reproduce the Excel tracker's Firm × Fund × frequency logic as a structured, ops-editable config the tool can check against — the sheet stays the source of truth for expectations. Highest risk of quiet error — validate against several months of the existing sheet before the team relies on it. Watch for undocumented exceptions (wind-down funds, commitments not yet active, the ~10% of portals not on Canoe).

A3

Reconciliation + review queue

Rules engine matching received vs. expected; a dedicated queue for anything Canoe flagged or dated implausibly.

A4

Dashboard + alerts

Visual layer + overdue/anomaly notifications. Runs alongside the Excel process rather than replacing it — the dashboard takes over the routine "what arrived / what's outstanding" tracking, so the manual sheet takes far less time to keep current. The team decides how much of the sheet to keep.

A5

(v2, if approved) Data-date extractor

Drop the narrow LLM date-read into the review queue so most exceptions clear automatically. Purely additive — the v1 human queue remains the fallback for low-confidence reads.
